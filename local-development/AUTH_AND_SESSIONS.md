# Authentication & Session Cookies

How identity flows between services via Flask session cookies.

## How It Works

Flask uses **signed cookies** to maintain sessions. When `app.secret_key` is set, Flask
cryptographically signs a cookie (default name: `session`) sent to the browser. The cookie
contains a `session_id` — the actual session data lives server-side in **Redis**.

The signing ensures the client can't tamper with the cookie value. If the `secret_key`
differs between services, they can't read each other's cookies — which is why **all Flask
apps must share the same `SECRET_KEY`**.

## Session Flow

```
1. User logs in via Keycloak (Identity service)
2. Identity writes session data to Redis (keyed by a UUID session_id)
3. Identity stores session_id inside Flask's signed session cookie
4. Browser sends this cookie on every request (same domain required)
5. Any Flask service (MAS, RAG, Backend) reads the cookie → extracts session_id → looks up session in Redis
```

## Why Same Domain Matters

Cookies are domain-scoped. If Identity runs on `identity.example.com` but MAS runs on
`mas.example.com`, the browser won't send Identity's cookie to MAS. That's why nginx
proxies all services under the same domain (the `FRONTEND_URL`) — the cookie stays valid
across all `/api*` paths.

## Flask Configuration Reference

All 4 Flask services (Identity, MAS, RAG, Backend) share the same config keys:

| Config Key | Env Variable | Local Default | Production Value | Purpose |
|---|---|---|---|---|
| `secret_key` | `SECRET_KEY` | `""` (crashes if empty) | Generated secret stored in a K8s Secret | Signs the session cookie. **Must be identical across all services** so any service can decode the cookie another service wrote. |
| `session_cookie_secure` | `SESSION_COOKIE_SECURE` | `False` | `True` | When `True`, cookie is only sent over HTTPS. Must be `False` locally (HTTP) and `True` in production (HTTPS). |
| `session_cookie_http_only` | `SESSION_COOKIE_HTTPONLY` | `True` | `True` | Prevents JavaScript from reading the cookie (`document.cookie`). Always `True` — protects against XSS. |
| `session_cookie_samesite` | `SESSION_COOKIE_SAMESITE` | `"Lax"` | `"None"` | Controls cross-site request behavior. `Lax` locally (simple same-origin setup). `None` in production because the UI and APIs may be on different subdomains behind nginx — requires `Secure=True` to work. |

### Local vs Production Differences

| Setting | Local | Production | Why |
|---|---|---|---|
| `SESSION_COOKIE_SECURE` | `False` | `True` | Local dev uses plain HTTP (`http://localhost:5000`). Production uses HTTPS. Browsers reject `Secure` cookies over HTTP. |
| `SESSION_COOKIE_SAMESITE` | `Lax` | `None` | Locally everything is on `localhost` so `Lax` works fine. In production, the UI may make cross-origin requests to API services (even if proxied, the browser sees different paths/ports during development of Helm charts). `None` + `Secure=True` allows the cookie to be sent on all cross-origin requests. |
| `SECRET_KEY` | Auto-generated by `unifai-dev init` into `.env` files | Stored in a Kubernetes Secret, injected via Helm post-sync hook (`helm/scripts/shared-resources-postsync.sh`) | Locally each developer gets their own key. In production it's a single shared secret across all pods. |
| `FRONTEND_URL` | `http://localhost:5000` | The actual cluster URL (e.g. `https://unifai-ui-....openshiftapps.com`) | Determines CORS `origins` — must match exactly what the browser sees in the address bar. |

## CORS Configuration

Each service configures CORS with `supports_credentials=True`:

| Config | Value | Purpose |
|---|---|---|
| `origins` | `FRONTEND_URL` env var (default `http://localhost:5000`) | Only this origin can make credentialed requests. Must match the UI's actual origin exactly. |
| `supports_credentials` | `True` | Tells the browser "yes, send cookies with cross-origin requests to this API". Required for the session cookie to be included in fetch/XHR calls. |

## Environment Variables

| Variable | Where | Required | Notes |
|---|---|---|---|
| `SECRET_KEY` | All Flask services | Yes (app crashes without it) | Must be the same value everywhere. `unifai-dev init` auto-generates this locally. In production: K8s Secret via Helm post-sync. |
| `FRONTEND_URL` | All Flask services | No (defaults to `http://localhost:5000`) | The URL nginx serves the UI from. In production this is the real cluster URL (HTTPS). |
| `SESSION_COOKIE_SECURE` | All Flask services | No | `False` locally (HTTP), `True` in production (HTTPS). |
| `SESSION_COOKIE_SAMESITE` | All Flask services | No | `Lax` locally, `None` in production (cross-origin with `Secure`). |

## Nginx — The Cookie Gateway

Nginx (`ui/deployment/nginx.conf.template`) is the single entry point for all browser
traffic. It serves the UI and reverse-proxies API calls to each backend service:

```
Browser (https://unifai.example.com)
  │
  ├── /          → UI static files
  ├── /api1/*    → RAG service
  ├── /api2/*    → Multi-Agent service (MAS)
  ├── /api3/*    → Identity service
  └── /api4/*    → Platform Backend
```

### Why This Matters for Cookies

Every proxied location includes `proxy_cookie_path / /` — this rewrites the cookie's
`Path` attribute so that a cookie set by Identity (on `/api3/`) is valid for all paths.
Without this, the browser would scope the cookie only to `/api3/` and never send it to
`/api2/` or `/api1/`.

Because all services are accessed via the **same nginx host**, the browser sees one domain
and happily sends the session cookie on every request regardless of which `/apiN/` path
the request targets.

### Key nginx directives for cookie/auth flow

| Directive | Purpose |
|---|---|
| `proxy_cookie_path / /` | Ensures cookies set by any backend are available on all paths |
| `proxy_set_header X-Forwarded-Proto $scheme` | Lets backends know the original protocol (HTTPS) — important for `Secure` cookie decisions |
| `proxy_set_header Host $host` | Preserves the original `Host` header so cookie domain matching works |
| SSL termination (`ssl_certificate`) | nginx handles TLS; backends communicate over plain HTTP internally. This is why `SESSION_COOKIE_SECURE=True` works — the browser sees HTTPS even though backend-to-backend is HTTP. |

### Local Dev vs Production

In **local development**, there's no nginx — the Vite dev server proxies API calls
directly to each Flask service on `localhost`. Cookies work because everything is on the
same `localhost` domain.

In **production**, nginx is the single TLS-terminating reverse proxy. All services hide
behind it, sharing one domain and one cookie scope.

---

## CLI Special Case

The CLI can't use browser cookies natively. After SSO login, the Identity service returns
the signed cookie value to the CLI, which stores it locally and re-sends it as a cookie
header on every API request.

## Where This Is Applied

Each service's `flask_app.py` (the application factory) sets these configs identically:

- `multi-agent/adapters/inbound/flask/flask_app.py`
- `backend/api/flask/flask_app.py`
- `rag/bootstrap/flask_app.py`
- `shared-resources/identity/bootstrap/flask_app.py`

The config values come from each service's `config/app_config.py`, which reads from
environment variables (populated by `.env` files locally, Helm values in production).
